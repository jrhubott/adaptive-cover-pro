## Highlights

2026.8.0-beta.1 is the first curated release of the 2026.8 cycle, and the biggest one yet: 129 commits since 2026.7.6, four new physical cover types plus Cover Groups, and a full diagnostics triage engine with a read-only Troubleshoot step. I'm shipping this as a beta because the surface area is large enough that I want real installs exercising it before it goes stable — the new cover types (Louvered Roof, Sliding Curtain, Day/Night Shade, Dual-Panel) especially need feedback from people with the actual hardware, since I built them from spec and beta-tester reports rather than a shelf of every shade type. If you run any of the new cover types, Cover Groups, or the reworked config-flow wizard, I want to hear what breaks. Nothing here changes configured behavior for an existing install — see Upgrade Notes.

## Features

**Cover Groups — orchestrate a roster of covers as one unit (#790, #797, #802, #803, #804, #845, #922, #937):** I added a new virtual `cover_group` entry type. A group is a `GroupPolicy` with `is_orchestrator: ClassVar[bool] = True` on the policy base — `__init__.py` and every platform branch on that capability flag rather than a cover-type string, so setup routes to a new `GroupCoordinator` instead of a per-cover coordinator. Groups can hold both native ACP covers and generic `cover.*` entities, plus an optional linked area (`CONF_GROUP_AREA`) whose covers are unioned into the roster live and re-resolved on registry changes. Scenes (All Open / All Closed / Privacy) resolve per member through a `position_for_scene` policy hook and ride each member's own pipeline as a `GroupIntent`, arbitrated by two new handlers: `GroupSceneHandler` at priority 85 (above manual override, below weather safety) and `GroupLockHandler` at the safety priority (`CUSTOM_POSITION_SAFETY_PRIORITY`, 100), which freezes members in place. A configurable stagger delay (`CONF_GROUP_STAGGER_DELAY`) spaces out member commands, and per-member per-scene opt-out lets a member sit out a scene while lock still overrides it. I added bulk automation and Climate Mode switches, a Group Lock switch, Stop and Clear-Overrides buttons (sharing `async_reset_manual_overrides` with the member-level reset path), a scene-picker select, an opt-in aggregate cover entity (position/open/close/stop, on by default), and rollup sensors — Group State, Active Scene, Group Climate Mode (via the shared `climate_mode_from_diagnostics` helper), and a Group-Driven Members "who-won" sensor built from each member's `pipeline_winner_name`. Six `group_*` services (`group_activate_scene`, `group_set_position`, `group_lock`/`group_unlock`, `group_clear_overrides`, `group_set_automation`, `group_stop`) let automations drive a group directly, and group entries surface their own diagnostics rollup and area membership. A same-cycle fix caught the three text/status group sensors (Group State, Active Scene, Climate Mode) setting an empty-string unit of measurement to hide from the logbook — HA raises on a non-numeric value when the unit isn't `None`, and `""` is not `None`, so the state write aborted and the entity went unavailable the moment it held a string; I dropped the unit from all three (#843, #844).

**Louvered Roof cover type for bioclimatic pergolas (#830, #831, #833, #894):** I added a `cover_louvered_roof` sensor type for pergola/Lamellendach slats that rotate in a horizontal or pitched roof plane, reusing the venetian slat cut-off solver (`slat_cutoff_angle`) against a profile angle taken relative to the roof plane and gated by the roof-window angle-of-incidence test (`roof_slope_ratio`). It drives through the existing tilt axis, so nothing else in the pipeline needed to change. Follow-ups refined the model against real installs: a far-side branch selection so evening sun (where `cos(gamma) < 0`) tilts the correct direction instead of a mirrored angle, a configurable max slat angle for drives whose physical travel isn't 90 or 180 degrees, an inverted objective — pergola slats now optimize for the most-open angle that still blocks direct sun rather than the venetian's steepest-cutoff — and a widened slat depth/spacing range with pergola-scale defaults. After beta-tester validation against measured data, I also corrected `_blocking_depth()` to account for interlocking-lamella overlap (`2*depth - spacing` rather than nominal depth), which had been over-closing the slats by 8-9 degrees (#830, #916).

**Sliding-Curtain cover type with shade-area percentage close (#829, #832):** I added a binary sliding-curtain cover type that fully closes when direct sun enters the window's field of view and opens otherwise, then extended it with a two-point floor "shade area" option so the curtain closes only as far as needed to keep that area out of direct sun — a continuous percentage, with slide direction left/right/centre-parting — instead of a flat binary close. The ray-to-window-plane projection was factored out of the vertical blind's glare-zone math into a shared `engine/sun_geometry.py` helper both features now reuse.

**Day/Night Shade cover type — Models A/B/C (#993, #995):** I added a `cover_day_night_shade` type for dual-fabric cellular shades (sheer + blackout), reinterpreting the tilt axis as the middle-rail fabric blend and reusing the venetian `DualAxisSequencer` by composition. Climate-aware fabric selection picks sheer when comfortable and blackout when hot summer sun exceeds the sheer's opacity, through one `_compose_blend` seam shared by live resolve and forecast. Three control models cover different hardware: Model A drives position + tilt directly; Model B (`split_range`) projects the (coverage, blend) pair onto a single position axis for single-motor drives; Model C (`dual_entity`) drives two independent `cover.*` rail entities via a new `resolve_entity_target` policy hook, folding the blend into the middle rail's absolute position while the bottom rail follows coverage.

**Dual-Panel cover type — independent sheer and blackout (#996, #1000, #1035, #1039):** I added a `cover_dual_panel` type for two independent shades over one window — a sun-tracking sheer front and a trigger-deployed blackout back — built on the same `resolve_entity_target` seam, using a pure `compute_layered` helper. Unlike Day/Night Model C, the two layers have no coupling, so they move independently. A follow-up fix closed a bug where the back panel's inverse/interpolation frame leaked in from the front panel's own state: `resolve_entity_target` now always derives its own inverse/interpolation frame from options rather than the caller's, fixing an inverse-install case where the blackout panel dispatched to the wrong physical end.

**Unified tilt-axis config across cover types, plus a specify-angles calibration mode (#768, #964, #966, #957, #962):** Thanks to [@derabbink](https://github.com/derabbink), who added a third `tilt_mode`, `specify_angles` ([#768](https://github.com/jrhubott/adaptive-cover-pro/pull/768)), letting users declare the raw slat angle at 0% and 100% tilt (`tilt_angle_0`/`tilt_angle_100`) to calibrate non-standard slat geometry. I then generalized the tilt-band controls — min/max tilt, the sun-only flags, the safety margin, and the clamp/proportional transform — so every tilt-axis cover type, not just venetian, gets them, via a shared `tilt_limits_schema()` and a `PositionConverter.apply_tilt_limits` primitive that `AdaptiveTiltCover.calculate_percentage` now self-applies (venetian keeps its own `_clamp_tilt` seam, so there's no double application). I also added an opt-in "proportional" slat tilt transform: instead of flat-capping the calculated tilt demand at Max Tilt, it linearly remaps the full 0-100% solar demand onto the configured [Min Tilt, Max Tilt] band, preserving the sun-position-to-slat-angle relationship across the whole usable range. `CONF_VENETIAN_TILT_SAFETY_MARGIN` was renamed to `CONF_TILT_SAFETY_MARGIN` (legacy key kept migration-read-only, rollback-safe).

**Sensor-gated min/max constraints for Custom Position slots (#943, #958):** Custom Position slots could previously only replace the resolved position/tilt with a fixed value — a window contact asking for "at least 50% open" would also drag a calculated 75% back down. Each slot now takes three optional numeric limits (max position, min tilt, max tilt) that clamp the resolved value instead of replacing it, so solar tracking and weather handling keep their normal precedence. I unified this with the existing floor/tilt-fixed logic behind one `AxisConstraint` model in `pipeline/axis_constraints.py`, with the floor and tilt-axis handlers now delegating to it as thin adapters.

**Generalized `set_axes` service with axis self-discovery (#725, #848, #886, #887):** I added a single `adaptive_cover_pro.set_axes` service that takes a per-axis target map (position/tilt) plus force, introspects the cover's declared axes, and dispatches through a new `async_apply_user_axis` collapse point — `set_position`/`set_tilt` are now thin wrappers over the same path. I also added an additive `cover_discovery` sensor attribute describing every cover type's axes (id, label, range, unit, capability, supported), which the companion Lovelace card uses to build its controls generically. A follow-up fix taught the axis model that the position axis is still drivable via `open_cover`/`close_cover` fallback on covers with no native `set_cover_position` — `CoverAxis` gained a `drive_fallbacks`/`is_drivable()` model so `set_axes` no longer wrongly rejected position on open/close-only covers.

**Forecast now projects the secondary axis (venetian tilt) (#724, #849):** the position forecast previously only projected the primary position axis. I grew `ForecastSample` with a generic axes map and added a polymorphic `forecast_secondary_axes` policy hook; the venetian policy now projects the tilt track per forecast step by reusing the same tilt math the live pipeline uses, so the forecast matches what the cover will actually do.

**A rules engine and a read-only Troubleshoot step surface config problems in plain language (#970, #972, #1007, #1016):** I built a pure, HA-import-free rules engine in `diagnostics/triage.py` — a `Severity`/`RuleInput`/`Finding`/`TriageRule` seam evaluated by `run_triage()`, with each finding keyed by a frozen `TriageCode` and rendered through a `troubleshoot_i18n` bundle (mirroring the existing `reason_i18n` mechanism). `diagnostics/resolve.py` unifies the two previously-divergent ways of reading diagnostics (coordinator data vs. the cached diagnostic payload) behind one `read_diagnostics()` call that never triggers a refresh. A new read-only `async_step_troubleshoot` options-flow step runs the triage engine against live diagnostics and renders findings as a menu that routes each one to its relevant options step. I also migrated the config summary's existing "Cover Warnings" rules onto the same engine, byte-identical to the legacy output, so both surfaces share one rule table instead of drifting independently. The rule set has grown to 26 checks across three merges — the initial 11 seed rules, a backfill of rules 11-24 (including `MIXED_TEMP_UNITS` for mismatched °F/°C sensors), rule 25 (`ENDPOINT_POSITION_NOT_TRACKING`, #1026, #1073) for a one-way RF cover that claims open but keeps reporting 0, and rule 26 (`WEATHER_OVERRIDE_INVERTED`, below) — and I pointed the offline issue-triage tooling at the same `run_triage()` function used at runtime.

**Diagnostics gain four non-sensor health checks: unreachable covers, inverted config, and a missing sun (#973, #975, #977, #979):** I added Repair-based health checks for failure modes the existing sensor-availability watchdog couldn't see: a controlled cover that's unavailable or missing, a position envelope with min above max (or a custom slot outside it), a time window where start is at or after end, and a `sun.sun` entity that's unavailable or missing. All four are informational, auto-clearing Repairs sharing the same 900-second debounce as the existing sensor health check, so a restart or a brief blip doesn't nag. I factored the shared debounce/raise/clear/shutdown lifecycle into one base class shared by the existing sensor-availability manager and the new config-coherence manager. Follow-up passes closed real gaps: a stale Repair now clears itself on the first healthy check after a config-entry reload, the envelope check no longer false-fires on slots that never deliver a fixed position, and removing a cover now sweeps its orphaned Repair instead of leaving it until an HA restart.

**Two more health checks: covers that never reach their commanded position, and tilt cover types on non-tilt hardware (#990, #991, #992, #1004):** I added a check that raises when ACP commands a cover to a position it never reaches within the debounce window, reusing the read-only tolerance check already used to decide when a command is settled. It's guarded against nagging a healthy cover: it returns clean for a My-preset target on an open/close-only device, in dry-run mode, and it gates on the cover's actual commanded axis rather than raw position support so tilt-fallback covers stay covered. I also added a check for a tilt-declaring cover type (tilt, louvered roof, venetian) bound to a device whose reported features lack tilt-position support. That test lives on a polymorphic `tilt_capability_contradiction()` policy hook so the coordinator never branches on cover-type strings; Day/Night Shade overrides it to skip Models B and C, which are position-only and would otherwise raise a Repair that never clears.

**New `get_troubleshooting` service exposes Troubleshoot findings outside the options flow (#1059, #1066):** I added a `get_troubleshooting` service so the Lovelace card, automations, and offline triage can read the same findings the Troubleshoot step shows, without walking the config UI. Both surfaces now go through one seam, `build_troubleshoot_result()`. I gave it per-entry error isolation — one bad instance no longer takes down the whole response — and one consistent response shape across a healthy read, a CONFIG-only partial result, and a total failure, so a consumer never has to sniff error text to know whether findings are trustworthy. Naming a cover group or a Building Profile (neither of which has diagnostics) now raises a clear validation error instead of crashing.

**Triage rule for an inverted weather override (#1094, #1100):** `weather_override_position` is handed to the cover verbatim, so its schema default of 0 is the safe retracted endpoint on an awning but the fully-deployed endpoint on a blind. Set it wrong on a shade and every gust drives the fabric out into the wind, holds it for the timeout, then retracts — I hit this on my own deck shade and only found it by correlating history against the wind sensor by hand, eleven deploy/retract cycles in under three hours. Rule 26 fires when the override is more deployed than the idle default, reading the polarity off the axis descriptor the policy already owns rather than hardcoding "shades want 100," so it fires correctly whether the cover is an awning or a blind. It's gated on weather being enabled with a trigger source configured, and excludes min-mode entirely, where the same value is a floor clamp with different semantics.

**Pipeline decision-trace reasons are now localizable (#882, #909):** The "why did this handler act" strings shown in the decision trace and sensor attributes used to be hardcoded English prose assembled inline in each handler. I introduced a frozen `ReasonCode` vocabulary and a `Reason` payload type, plus a `reason_i18n` bundle (English source of truth, mirrored into German and French) resolved through a shared loader. Every pipeline handler — solar, weather, default, group, manual override, occupancy, cloud suppression, glare zone, custom position, and climate — now emits a `Reason` on the pipeline result instead of a raw string, with the registry deriving byte-identical English output when no localized template applies yet. The calculation engine exposes the same mechanism as `control_state_reason_code`, keeping the reason vocabulary in the pure engine layer while localization happens only at the diagnostics/sensor boundary.

**Config-flow "How It Decides" summary sorts by effective priority and shows custom slot names (#910, #915, #923, #926):** The Configuration Summary's decision-chain section used to print rules in a fixed category/slot-ID order, so a custom slot at priority 77 could appear above one at priority 80, and it always labeled custom slots as `Custom#{slot}({priority})` even when the user had named the slot. I now order the whole chain by descending effective priority (ties broken by evaluation order, so built-ins outrank custom slots at the same priority), with the priority badge rendered as a leading bold prefix. Both the summary chain and the priority-ladder preview now render the configured custom slot name when set, falling back to `Custom#{slot}({priority})` otherwise.

**New condition templates for severe weather and manual-override input (#974, #982):** I added `weather_severe_template` (plus a combine mode) as a per-cycle folded condition mirroring the existing `is_raining`/`is_windy` templates, and `manual_override_input_template` as a rising-edge trigger mirroring the input-sensor edge path. Both are exposed through the `set_option` service and counted in the config summary alongside the existing weather-safety templates.

**`linear_position` attribute exposes the pre-interpolation target (#911, #914):** The Cover_Position sensor's state reflects the interpolated motor command, which can differ from what the user actually configured once interpolation curves are applied. I added a purely additive `linear_position` attribute carrying the pipeline's pre-interpolation logical target, plumbed through the diagnostics builder the same way the existing raw-calculated-position attribute is, so the companion Lovelace card can show the configured value alongside the interpolated one.

**Diagnostics now report each temperature sensor's unit (#969, #1002):** I added a nullable unit-of-measurement field to the sensor-source diagnostics model, populated at both the sensor-sources and inside-temperature climate call sites. This is what feeds the new `MIXED_TEMP_UNITS` triage rule above — a read-only payload enrichment with no new config keys.

**Config-flow create wizard rework — per-slot options pages and a geometry-only setup flow (#945, #946, #948, #949):** I turned the three flat options-flow areas that used to render every custom-position, blind-spot, and glare-zone slot on one long form into per-slot sub-menus — each area lists its configured slots plus an Add entry, and picking one opens a focused single-slot page that returns to the menu on save. Storage is unchanged, so there's no migration or config-entry version bump. I then stripped the create wizard itself down to the one thing with no safe default — the cover(s) and their physical geometry, window azimuth especially — dropping the entire post-geometry create flow (sun tracking, position, behavior, blind spot, interpolation, automation, overrides, custom position, motion, light/cloud, climate, weather) since the options flow already covers every one of those steps. A follow-up fix swapped the summary's literal wiki URL for a placeholder after Hassfest's CI job started rejecting literal URLs in config/options step strings.

**Optional custom names for custom position slots (#867, #871):** I added an optional per-slot name field to custom position slots. When set, the name overrides the label shown in the pipeline reason string, the decision-trace active-slot-name attribute, and the ACP Lovelace card snapshot, for both boolean- and template-triggered slots. Leaving it unset keeps the byte-identical old behavior.

**Sun-relative manual override duration modes (#1044, #1046):** I added a `manual_override_duration_mode` select so a manual-override hold can end at a sun event or the schedule window's end instead of only after a fixed number of minutes — `fixed` (default, unchanged), `until_sunset`, `until_sunrise`, `until_next_sun_event`, `until_window_end`. The deadline is the first occurrence of the chosen event strictly after the override started, resolved through the existing sunset/sunrise definition so custom time entities and configured offsets still decide what "sunset" means; when an anchor can't be resolved, the hold falls back to the numeric duration and the configuration summary gets a warning line for that case. Along the way I collapsed five scattered copies of the start-plus-duration expiry formula onto a single `expiry_for()` authority on the manual-override manager, backed by a `manual_control_expiry` pin store. No config migration — an absent key reads as `fixed`.

**Apply Calculated Position button (#1045, #1047):** The delta-position and delta-time gates can hold a freshly calculated target back indefinitely, and there was no way to say "apply what you just calculated, now." I added a per-entry button that refreshes, then force-dispatches the current cycle's pipeline position past both gates, following the My Position precedent that an explicit press is a user command. It still respects the master kill switch, the cover-unavailable boundary, and the same-position relay-click gate, and it skips covers under a live manual override rather than punching through and having the override handler re-assert the hold next cycle. Two audit passes narrowed the hold-bypass to only the two control methods whose held position is a cross-cover mean (Group Lock and Motion Timeout), after finding the naive version could drive a group-locked pair to their mean position or freeze an entire multi-cover instance over one manually-overridden member.

**Auto-resolve indoor temp sensor from HA area (#786, #840):** A cover with no explicit `temp_entity` now falls back to the temperature entity configured on its Home Assistant area, gated by a new `auto_resolve_temp_from_area` toggle (default on, per-install opt-out). Duplicating a cover no longer copies the per-room indoor temperature sensor either, since that value is area-specific. When the resolved sensor stays unavailable past a debounce, ACP raises an informational Repair rather than silently falling back further, and the resolved entity plus its provenance surface in diagnostics and the configuration summary.

**Rename "Field of View" to "Sun acceptance angle" (#604, #883, #938, #940):** "Field of view" describes what an observer looks out at; the `fov_left`/`fov_right` parameter is the opposite — the angular half-window from which direct sunlight is accepted into the window. I renamed the user-facing wording to "Sun acceptance angle," matching the term the engine already used internally, across config/options-flow labels, `services.yaml`, the configuration-summary bundle, and card-facing decision-trace strings. Scope is display strings only — the `fov_left`/`fov_right`/`fov_compute` option keys are unchanged, so there's no config migration. A follow-up fix corrected the French translation, which had rendered the new concept as an anglicism, to the established French optics term.

**Rename Motion Override to Occupancy Detection; add `set_occupancy` service (#723, #878, #880, #881):** I renamed every user-facing "Motion Override"/"Motion" display string to "Occupancy Detection"/"Occupancy" so the label matches what the feature actually reacts to — room occupancy from motion sensors, presence sensors, and media players, not raw motion alone. This is display-only: the `set_motion` service, its option keys, entity unique IDs, and every translation JSON key stay frozen, so nothing breaks for automations, dashboards, or the companion card. I then added `set_occupancy` as the current-name service, taking `occupancy_sensors`/`occupancy_media_players`/`occupancy_timeout` and delegating to the same handler as `set_motion` through a field-alias mechanism, so there's one handler body. `set_motion` keeps working but now logs a deprecation warning pointing to `set_occupancy`. A follow-up fix caught the rename missing the pipeline's own `motion_timeout` handler reason strings, which still leaked "motion timeout" into the card's decision trace.

**Configurable seasons for glare tracking (#548):** Thanks to [@dns13](https://github.com/dns13), who added a `tracking_seasons` climate option that limits glare tracking to selected seasons, defaulting to all seasons (unchanged behavior). Dedicated winter-heating/insulation and summer-cooling rules still run ahead of the gate regardless of the selected seasons, so a deselected season only suppresses the neutral glare-tracking fallback, not the climate strategies that matter more.

**Hold-time and hysteresis for climate temperature thresholds and cloud suppression (#864, #873, #917, #919):** I moved the cloud-suppression activate/deactivate decision out of the pure pipeline handler into a stateful manager that owns per-trigger latches and a hold timer, resolving one `cloud_suppression_active` bool into the snapshot. A new `cloud_suppression_hold_time` option (0-3600s, default 0) and optional per-trigger release thresholds for lux/irradiance/cloud-coverage let a sensor hovering near a threshold stop flapping the cover. I then mirrored the same primitive onto climate mode's temperature crossings via a shared smoothing latch/debounce and pure crossing functions. Both features default to instantaneous behavior, so existing installs are byte-identical with no config migration.

**Extreme-heat all-day close via a unified climate seam (#842):** A new outdoor-temperature "extreme heat" strategy (`temp_extreme_heat` threshold, `extreme_heat_position`) force-holds the cover at a configured position all day regardless of sun position, FOV, time, or presence — for heatwaves where a hot wall keeps radiating after the sun leaves the window. It's implemented as an override band built from the existing climate-rule seam and prepended to all four climate rule tables, so it pre-empts even winter heating on a briefly-cold heatwave morning, while reusing the existing tilt/inverse-state/interpolation dispatch path rather than duplicating it. When the threshold is unset the band is inert and every existing outcome is byte-identical.

**Conservative, directional position rounding (#978, #988, #981):** Thanks to [@FredM67](https://github.com/FredM67), who added `calculate_raw_percentage()` on the base engine cover to expose the unrounded geometry result, then applied directional rounding everywhere a raw solar percentage gets turned into a command — floor for blinds/tilt/venetian (0% = closed = full coverage), ceil for awnings (100% = extended) — rather than the plain `round()` every site used before, which could round toward less coverage than the geometry actually demands. The same follow-up fixed an earlier plain rounding bug in the field-of-view derivation itself, where `fov_from_reveal()` rounded down and could shorten the active tracking window versus what the reveal geometry requires; that switched to `ceil()` too.

**Signed-gamma blind spot, evaluated in the cover's own acceptance frame (#247, #913, #918):** Blind-spot obstruction edges are now stored as signed gamma offsets from the window normal — the same frame as the sun-acceptance angle — replacing the old field-of-view-relative storage, via an additive, rollback-safe migration that seeds the new keys while the legacy ones stay migration-read-only. The blind-spot test now runs through the same polymorphic angle hook that acceptance already uses, so a tilted roof window correctly masks obstructions its near-flat glass physically sees, with no change for vertical/awning/tilt/venetian covers. Two audit passes hardened the service layer so `set_blind_spot`/`set_option` convert legacy edges to the new keys instead of silently no-opping, and a call supplying only one legacy edge completes the pair from the live back-converted value rather than a frozen legacy one.

**Forecast sampling densified, and a forecast-aware climate temperature source (#602, #547, #879, #846, #912, #920):** Forecast sampling moved from a 15- to 10-minute step for a smoother companion-card curve, staying comfortably under HA's attribute-payload limit. Climate mode also gained an `outside_temp_source` option (`forecast_max` / `max_of_live_and_forecast`) that pulls today's daily forecast max from the configured weather entity instead of only the live reading, with a config-flow warning when a forecast source is selected but no weather entity is configured.

**Gate the min-mode floor clamp on priority so a manual move isn't silently pulled back up (#472, #908):** A min-mode position floor previously clamped every ACP-mediated user command up to the floor regardless of the floor slot's own priority. The user-move clamp now only applies when the floor's priority is strictly above manual override's priority 80 — a floor above 80 still blocks a manual move, one at or below 80 yields to it. The separate pipeline-winner clamp for auto-rule composition is unconditional either way and unaffected.

**Generalized "force endpoint" from venetian to every position-capable cover type (#897, #898):** When `endpoint_use_open_close` is on and the target is a mechanical stop, blinds and awnings now also route to `close_cover`/`open_cover` instead of `set_cover_position` — not just venetian — via a new polymorphic predicate, so a cover parked within the position tolerance of the endpoint reaches its true final position instead of stalling a percent short. The existing anti-relay-click latch still fires the endpoint command exactly once per transition.

**"My" assumed position surfaces consistently across a user stop (#888, #889, #890, #892, #896, #899):** Several related fixes converge on one goal — a Somfy-RTS-style open/close-only cover stopped mid-move should show its configured My-position value, not a stale 0/100. The assumed value is now recorded even when a user stop lands mid ACP's own move, recorded from the dedicated stop service path too (which the external stop→My detector otherwise skips), and wins over the open/closed→100/0 mapping for assumed-state covers rather than being wiped by it, since open/closed there is only the last commanded direction, not a real read. A user stop now also triggers a debounced coordinator refresh so the card updates within seconds instead of waiting for the next scheduled cycle.

**Card-visible "opening/closing" state for no-feedback covers (#893):** Somfy-RTS-style open/close-only covers report neither a position nor an opening/closing HA state, so a card had no way to show a commanded move in progress. A new per-entity transit direction is set alongside the existing ~45-second transit-timeout window, derived from the routed target versus prior position, and exposed as an attribute on the Cover_Position sensor and in diagnostics — clearing exactly when the transit timer clears.

**Manual-override events now record who or what triggered a stop (#875, #876):** A detected "My position" override from a stop command now captures the originating HA context (user, automation, or script) and records it in the manual-override diagnostics event, making a phantom-trigger report self-attributing without needing the HA logbook.

## Fixed

**The tilt safety-margin slider did nothing at everyday sun angles (#1089, #1102):** The slider scaled the geometric safety margin's excess over 1.0, but inside the normal operating envelope (`|gamma| <= 45°`, `10° <= elevation <= 75°`) the geometry's own margin is exactly 1.0, so the excess was zero and raising the slider had no effect for most of the day. I added a flat slack budget on top of the geometry's own margin instead of scaling it, sized from the same geometric maxima the calculator already uses, so a maxed slider always grants at least as much slack as the most extreme sun angle would demand unaided; `safety_margin = 0.0` stays a byte-for-byte no-op at every geometry. The margin still can't move a slat the solve has already parked on a travel limit — fully open, fully closed, or the edge of a narrowed Minimum/Maximum Slat Tilt band — so I rewrote the description (and the German/French translations) to state that as a general rule rather than the wrong per-cover-type claim I tried first.

**Venetian tilt rounded the wrong direction on MODE2, leaking sun (#1090, #1103):** The dual-axis tilt sub-path never picked up the directional rounding described above. My first attempt floored the raw percentage, but MODE2 maps 0-180° onto 0-100% with 90° (horizontal) as maximum openness, so coverage bottoms out at 50% and grows toward both ends — flooring above 50% moves the slat toward horizontal, the leaking direction. I added a `round_toward_coverage()` hook, overridden on the tilt engine cover to round away from whichever percentage maps to horizontal (MODE1's pivot is 100%, so it still floors for free). Both the venetian tilt sub-path and the tilt-only solar branch now go through this hook. A follow-up fix re-bands the rounded integer so quantization can't push a value that started inside the configured min/max tilt back out past the cap.

**MODE2's non-monotonic coverage broke quantization at three more sites (#1104):** The minimize-movements quantizer and the "more protective position" comparison (plus a third site in the venetian policy) still assumed coverage is monotonic in the position percentage, which is false for MODE2. Both now consult two polymorphic engine hooks describing the coverage pivot and travel bounds, so a coverage "level" on a bi-directional axis is measured as a distance from the band-clamped pivot per side, and quantization never crosses it. An axis reporting no pivot runs the original code unchanged. The audit round this needed also caught a case that could command 100% on shipped defaults with minimize-movements on and Max Slat Tilt at 60, and a specify-angles calibration whose covering end the quantizer had backwards.

**A sub-degree Maximum Slat Tilt raised `ZeroDivisionError` on every cycle (#1105, #1108):** The louvered-roof/tilt effective-max-degrees calculation truncated the configured max slat angle with `int()`, so any stored value between 0 and 1 stayed truthy — bypassing the "use the mode default" sentinel — and became a literal zero denominator, crashing position calculation uncaught. I dropped the truncation so the denominator stays a float, and added a dedicated validator that rejects a sub-one-degree, non-zero value at both the options-service and import-config boundaries while still passing the sentinel and unset value through.

**Climate-mode tilt picked the sun-leaking slat hemisphere half the time (#1088, #1093):** The MODE2 winter-climate angle-to-percent mapping branched on the sign of gamma, but slats rotate about an axis parallel to the facade, so the sun's left/right offset only reaches the geometry through a term where cosine is even — the branch was both discontinuous and, on one side, picked the hemisphere that let direct sun through (up to nearly 7 cm of open aperture at the tested summer geometry). I removed the branch entirely, settled empirically across roughly 16,000 elevation/gamma points that one hemisphere strictly dominates, and dropped the now-dead parameter from the function signature so the trap can't be reintroduced.

**A proxy tilt slider didn't round-trip on venetian and tilt-only-hardware installs (#1034, #1038):** The tilt-read inversion check derived its answer from the cover's first declared axis, which is only the tilt axis for tilt/louvered-roof covers — a venetian carries tilt as its second axis, so dragging the slider to 30 wrote 70 to the source but read the same 70 back unmirrored. I replaced the positional index with an attribute-owner lookup that finds the declared axis whose state attribute is the tilt position and derives inversion from that axis's own descriptor. The same pass fixed a blind or awning on tilt-only hardware with Inverse State, which routed through the identical split, and fixed Day/Night Shade for free since its import path merges an unvalidated inverse-tilt key wholesale.

**Past 90° off the window normal, a cover could slam shut or fully extend on a hundredth of a degree of sun movement (#1030, #1037):** A signed clamp on the cosine of gamma flipped sign exactly at 90° off the window normal, driving a projected length negative and clipping it to zero — a vertical blind snapped from 100% to 0% on a 0.01° azimuth step; tilt, venetian, and drop-arm awnings inherited it, with drop-arms failing the other way (full extension). I promoted the illumination test to a polymorphic angle-of-incidence property folded into the existing sun-behind-plane check, so past-90° now routes to the default position instead of a division blowup. Pitched roof windows and flat louvered roofs, which legitimately see gamma past 90°, delete their now-duplicate overrides; horizontal awnings opt out in area-shading mode so patio shading stays extended. The four bespoke clamps collapse into one shared foreshortening helper, and the roof-window slope-ratio calculation moves to exact dot products, removing a measurable accuracy error at steep roof pitches.

**A user command and the pipeline's own published data disagreed about which "frame" a position was in (#1027, #1028, #1033, #1036, #1043):** The automatic path inverted and interpolated a position before dispatch, but a user command (set_position, set_axes, set_tilt, the proxy cover, My Position, group member dispatch) handed its value straight through uninverted — on an inverse-state instance, the pipeline's 100 and a user's 100 drove the cover in opposite directions. I routed the user path through the same inversion/interpolation site the automatic path uses, extracted one `axis_inverted()` source of truth for "is this axis effectively inverted" (deleting three copies of the same formula), and normalized the linear-position sensor, the group entity's aggregation, and the proxy's tilt read to the same logical frame. A follow-up found the dispatch boundary was still inferring "already in the cover's frame" from unrelated flags rather than the value's actual frame — on an inverse-state or calibrated install, a "minimum 25% open" floor could dispatch its raw number and open the cover to 75% instead of the intended 25%. I deleted that inference entirely, since the pipeline result is contractually always in the logical frame; this intentionally reverses an earlier shipped behavior in favor of a strictly stronger frame-invariance guarantee, with no config migration needed since stored values already meant what the config flow says.

**The same-position gate resent commands forever on threshold-routed covers (#1095, #1101):** The gate compared the raw pre-routing target against the current reading, but a threshold-routed cover (open/close only, no position service) never has them match once the calculated position drifts inside the sub-threshold band — an identical close command went out every cycle even though the routed target hadn't moved. I broadened the gate to also compare the resolved current position directly against the routed target when the route isn't position-capable, which also covers a position-capable cover routed to open/close at a mechanical endpoint under `endpoint_use_open_close` (on by default). A resolved reading that contradicts the routed target still falls through to dispatch, so a stale stored target can never mask a genuine state change.

**Sun-appeared reconfirm re-fired a close command at an endpoint the cover already occupied (#985, #986):** In venetian tilt-only plus `endpoint_use_open_close`, the sun-just-appeared sentinel bypassed the same-position gate, resending a close command for a carriage already parked at the closed endpoint. On Somfy blinds that also drives the slats shut, so the unchanged target caused a real tilt disturbance ACP then had to restore. I scoped the reconfirm so it no longer applies when the target is a mechanical endpoint the cover already occupies, mirroring the idempotency the force-endpoint channel already respects.

**The venetian tilt axis silently dropped its target below the position-delta threshold (#954, #956):** The tilt axis was only serviced from the same-position branch of `apply_position`, so a below-threshold carriage delta skipped the command entirely and the tilt target was lost. I extracted the tilt-servicing call and invoke it from the delta-too-small and time-delta-too-small branches too, while confirming manual override still never services tilt and a forced cycle still can, even under override.

**Sensor/template inputs dropping out briefly caused false slot releases and false manual overrides (#1005, #1010, #1012, #1014, #1015, #1076, #1006, #1011):** An unavailable/unknown sensor read was coerced to the same "off" as a genuine False, so a transient dropout — during a `template.reload`, for instance — flipped a custom-position slot from on to off and force-dispatched every cover to its default position. The snapshot builder now distinguishes a valid off from a no-usable-value read and holds the slot's last-valid activation on an invalid read, generalized onto a shared grace-window state machine (anchored at the moment the input goes bad, not at its last good reading, since ACP has no update interval and can go 20 minutes between cycles at night). I applied the same pattern to climate's "Is Sunny" reading. Separately, a pipeline handler reevaluating mid-flight re-anchored the expected tilt from its own freshly recomputed result while ACP's own move was still traveling, so the actuator settling at the originally-commanded tilt no longer matched and was misclassified as a manual override; I sourced the expected value from the tilt ACP last actually dispatched instead.

**Discard latched target when manual override clears (#1052, #1053):** Cancelling a manual override could send the cover back to the override's own target instead of the freshly calculated pipeline position, because only the override-engaged callback discarded the stored target — the override-cleared callback never did, so a target latched during an override outlived it.

**Restore manual override and command target across HA reboot and reload (#1019, #1021, #1022, #1023):** The restore-entity callback fires during platform setup, but the manager's cover roster was populated later, during first refresh — so the restore guard saw an empty roster on every reboot and dropped every restored override. I moved the roster population earlier so the guard is valid by the time restore fires. Separately, after an integration reload the in-memory command-target store rebuilt empty, so a resting cover reported no recorded target and a context-less physical-remote move on it was wrongly rejected by the no-target rescue branch; I rehydrate the command target from the existing position-verification sensor on reload.

**Give custom-position, blind-spot and glare-zone slots a Delete (#1071, #1075):** The paged slot menu (see Features) offered only Add and Back, so the only way to remove a slot was to blank enough fields that it stopped rendering as configured — which hid the row without clearing it, and the next Add silently inherited the leftover flags. I added a shared slot-clearing helper that pops every stored key for a slot, plus a Delete row on each area menu.

**Profile/group edit steps return to menu; building profile sensors pre-fill in the create wizard (#851, #858, #1003, #1008):** Building Profile "Shared sensors" and the three Cover Group edit steps called the flow-terminal entry-creation call on submit, closing the whole options dialog instead of returning to the entry's menu — I conformed all four to return to the step menu like every other options sub-step. Separately, selecting a Building Profile during full setup stored only the link ID and deferred the sensor merge to entry creation, so every later wizard step rendered from a config missing the profile's keys; I now merge the profile in eagerly at select time.

**Clear a Building Profile sensor or template field (#1085, #1087):** Clearing a sensor or Jinja template in the Building Profile options flow never stuck — HA's frontend omits a cleared field from the submission entirely, and the profile-sensors step merged with a plain dict update, which never removes an absent key. Every sibling options step with the same field family already guarded this; the profile-sensors step was the one that hadn't. I applied the same guard, and fixed the other half of the bug where the merge-into-cover step was skipping (rather than removing) a now-cleared profile key on every linked cover.

**Blind-spot slot activation and FOV-span clamping (#852, #855, #868, #869):** Blind-spot slot 2/3's left marker had no default, so when the HA frontend omitted it at its minimum value (0), schema validation dropped the key entirely and the slot never activated; I gave it a default matching slot 1. Separately, blind-spot left/right are azimuth offsets within the sun-acceptance span, but nothing re-clamped them when the geometry step narrowed that span — a slot saved under a wider span could exceed the new one and mis-shape the runtime wedge. I added a shared clamping helper applied at all three span-change save sites.

**Copy Settings sync categories corrected (#862, #865):** Two automation-related fields were filed under the sun-tracking sync category rather than automation — the category shown on the config step where they actually live — so "Copy Settings to Other Covers" silently skipped them from the right bucket; I moved both. I also found the per-slot venetian tilt fields plus default/sunset tilt were absent from every sync bucket and never copied at all, and added them.

**Translation and label fixes (#961, #965, #967):** The venetian/tilt geometry step rendered several tilt-mode fields as raw keys, missing from the English translation entirely; the five venetian geometry selects used a bare enum, so HA rendered raw keys instead of translated labels; and the German Max Slat Tilt label had a typo. Fixed all three.

**Occupancy wording missed in decision-trace reason strings (#723, #881):** The Occupancy Detection rename (see Features) missed the pipeline's own motion-timeout handler reason strings, which flow verbatim into the card's position explanation — so users still saw "motion timeout active" on the card after the rest of the UI had switched terminology. Reworded the leaked strings; the frozen machine-readable status slug is unchanged.

**Localize config summary via instance-language fallback (#905, #906):** HA never populates the flow context's language for config/options flows, so the narrative configuration-summary block always rendered in English even though the localized bundles added for the original config-summary feature existed. I resolve the summary language from the instance's configured HA language instead.

**Set device manufacturer to Jason Rhubottom (#936):** The device manufacturer was still hardcoded to the name of the upstream integration this project forked from, so HA showed the wrong "by" attribution under every device.

**Enforce one time wire format across every write path (#1049, #1054, #1056, #1057, #1064):** Config import validated only keys with numeric range checks, so a start/end time from an imported backup could land in the config entry in a non-canonical shape — an imported "00:00" is not equal to the canonical blank-time sentinel, so every literal sentinel comparison across the integration read it as a configured time. Most sharply, the `until_window_end` override deadline then receded a day at every local midnight and never expired. I validate every time-typed option against one shared pattern regardless of write path, canonicalize what the config flow submits, and added a migration that repairs already-stored non-canonical values — a deliberate, documented exception to the additive-migration rule, since the rewrite only moves a value into the format every release already expects (see Upgrade Notes). I later found the Duplicate and Sync config-flow steps could still copy a stale value verbatim from a disabled entry, since a disabled entry never runs the migration; closed that write path too.

**Consolidate scattered sun-boundary and effective-default computations (#1048, #1050, #1051, #1055, #1058, #1060, #1068):** Several code paths independently recomputed pieces of the sunset/sunrise-boundary and effective-default logic and kept drifting out of sync with the main coordinator cycle — the `set_position` service's fallback branch dropped the custom sunset/sunrise time-entity override depending on which path evaluated it, the "sunrise offset falls back to sunset offset" rule was written out in five places (one of which defaulted to 0 instead), and the same fallback branch was dropping several more keyword arguments the effective-default calculation needed. I consolidated each of these onto one shared helper so every consumer reads from the same place.

**Make the coordinator the source of truth for switch state (#1063, #1065):** A cover's option switches (Automatic Control, Climate Mode, etc.) read a local cached flag that only the switch entity's own turn-on/turn-off ever wrote — so anything else that changed the underlying coordinator attribute directly (group bulk controls, the enable/disable/emergency-stop services) changed behavior while the switch kept reporting its old state, and being a restore entity, pushed that stale value back in at the next restart. Non-option switches now read the coordinator attribute directly. I also found the restore path treated any non-"on" restored state — including "unavailable"/"unknown" from an unclean shutdown — as off, which could silently flip a switch like Automatic Control to False with no user action; both the per-cover and group restore paths now share a guard that only counts genuine on/off history.

**Give the frame converters a pure home (#1042, #1069):** I moved the position-inversion helpers out of the manual-override manager into the already-pure position-utilities module, and swept every hand-rolled inline inversion check across the codebase onto the single shared helper. I also renamed the `floor_clamp_applied` field to `position_constraint_applied`, since the old name implied a meaning an earlier change had already removed.

**Awning overhang projection corrected; new window/area shade mode (#1025, #1031, #1032):** The horizontal awning was reusing the vertical blind's coverage-height math, which drops the azimuth foreshortening factor — awnings over-extended through the afternoon and jumped discontinuously as the sun crossed 90° off the window normal. I replaced it with the correct overhang geometry and added an `awning_shade_mode` option: "window" (default, the corrected overhang) or "area" (stays fully extended across the whole sun-acceptance span, for patio/area shading). A same-cycle follow-up fixed a crash this introduced: oscillating drop-arm awnings have no horizontal-geometry config, but the rewritten calculation unconditionally read a field only fixed awnings have, so the live pipeline raised an uncaught error whenever the sun was in the window's acceptance angle; I gave the oscillating-cover engine its own calculation path that never touches that field.

**A negative-tilt config field mis-cataloged as an unavailable sensor in diagnostics (#1017, #1018):** The Troubleshoot step's sensor-source diagnostics iterated the full building-profile sensor key set, which includes non-entity scalar keys like template bodies and combine-mode values ("or"/"and") — these got catalogued as entity IDs and flagged unavailable, producing garbled findings like a warning that "or" is unavailable. I split out an entity-only key set for iteration and added a defensive check that ignores any descriptor whose value doesn't look like an entity ID. A follow-up in the same fix caught the inverse gap: a fully-unavailable multi-sensor set had been skipped entirely by the same guard and produced no finding at all.

**Group-Driven Members sensor could latch a stale winner (#1082, #1084):** The sensor could freeze on an old value — reporting two members driven by Group Lock long after the group unlocked and both members had moved on to their own winners. The group only listened for member cover-state changes, so a winner change with no cover movement (a lock release, a motion timeout expiring) never reached it, and intent pushes went through HA's debounced refresh, so a second group action inside that window could publish a stale value. I subscribe the group directly to each member's coordinator and collapsed the duplicated intent-push call sites into one non-debounced path, so group actions land immediately and the who-won sensor always repaints.

**Suppressed false manual-override detection during venetian tilt drift-reset (#927, #928, #930, #934):** Venetian Tilt Drift Reset drives slats to a mechanical endpoint and back; on slow actuators the endpoint's tilt-position publish can land after the command-grace window expires, so the manual-override detector misread the stale endpoint publish as a large manual move. I added a one-shot, value-matched, time-boxed excursion record made when the reset sends its endpoint command, consulted by the detector before it flags a move as manual. A follow-up closed two more gaps in the same mechanism: mid-excursion intermediate publishes were still scored as manual moves, and the return-leg publish (which HA can deliver after the endpoint publish chronologically) needed the excursion record to track the whole out-and-back trajectory rather than being consumed on first sighting.

**Sunset/end-of-window dispatch overwrote an active custom position (#895, #902):** The astronomical-sunset transition and end-of-window default dispatch both bypassed the pipeline registry entirely and force-sent the raw sunset/default position, ignoring a higher-priority custom-position slot that already owned the result — a user's sleep-mode floor got overwritten by the default, then corrected back on the next refresh. Both fast-dispatch paths now check for an active override first.

**User card commands could be silently dropped as "same position" (#900, #901):** An explicit user command (card Open/Close/Set, `set_position`/`set_axes`, the My button) was swallowed by the same-position gate whenever ACP's raw view of the cover already matched the target — but on a no-feedback assumed-state cover, the raw HA state diverges from the assumed My display value, so pressing Open at My did nothing visibly. A new flag on the command context now bypasses the gate for genuine user commands, kept distinct from a plain force so recurring resends still get deduped.

**A routine solar/cloud cycle ignored the configured minimum interval (#853, #854):** An earlier lost-edge-recovery fix OR'd a "target changed" flag unconditionally into the force-dispatch decision, so any tracking cycle whose computed position merely differed from the last dispatched one forced past the delta-position/delta-time gates — meaning the minimum interval setting never actually applied while tracking. I scoped that flag's force contribution to safety/override results only.

**Forecast now uses the anticipated solar position (#1091, #1098):** The live solar handler switched to an anticipated (look-ahead) solar position calculation in an earlier release, but the forecast strip kept calling the raw geometry function, so the projected target has silently disagreed with the live pipeline ever since. I extracted the shared anticipation primitive and pointed the forecast at it with a horizon derived from the configured delta-time option; the live path itself is unchanged.

## Upgrade Notes

`ConfigFlowHandler.VERSION` stays 3; `MINOR_VERSION` moves to 12. Six new migration blocks landed this cycle (minor 7 through 12), and every one of them is additive — each either seeds a new key with `setdefault` or is a no-op version bump so an entry stops re-triggering migration on every restart. The one exception is the v3.11→v3.12 block, which repairs a `start_time`/`end_time` value already stored in a non-canonical shape (the #1049 fix above): that's a genuine rewrite of an existing key rather than only seeding one, but it's rollback-safe by construction — it rewrites the value into the exact canonical format every release, old and new, already expects, so an older build reading it after a rollback is strictly better off than before the repair, never worse.

Nothing here is breaking for an existing install. Upgrading changes no configured behavior on its own. New options this cycle — the awning shade mode, the tilt safety-margin key rename, the per-slot axis constraints, and the rest — either default to the byte-identical prior behavior or are seeded to preserve it, and light up only when you go looking for them in the options flow.
