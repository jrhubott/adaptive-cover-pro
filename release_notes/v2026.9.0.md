## Highlights

2026.9.0 is the September stable: 58 commits since 2026.8.3 across 209 files (+36,646/-1,660 lines). Two new capabilities anchor it — a per-cover solar-property surface feeding an Estimated Solar Gain sensor that reports the watts actually entering the room at the cover's current position, and named command queues that serialize transmissions across independent config entries, for the one-way radio backends where sixteen entries tracking the same sun collided freely. Three-point tilt calibration lets Specify Angles describe hardware whose slats reach horizontal somewhere other than the middle of their travel. A cluster of scoping options landed alongside: the weather override and per-slot custom positions can now stand down when the clock window shuts, sensor-gated bounds can keep clamping after it shuts, cloud suppression defers to an extreme-heat hold, and a tilt-only venetian carriage can stay pinned for solar wins alone. On the fix side, `PerEntityState.is_safety` finally has a defined lifetime across skips, resends and closed-clock cycles (#1165, #1225, #1311, #1313); the publish-lag guard that stopped false manual overrides on slow venetian actuators now covers tilt-only and day/night blend sends too (#1329, #1333); and both items 2026.8.0 shipped as Known Limitations — the sign-inverted vertical safety margin (#1173) and the coupled-cover-type hold verdict (#1179) — are closed here.

## Features

**Cover solar properties and an Estimated Solar Gain sensor (#1279, #1236, #1237):** I added an optional per-cover solar-property surface — `solar_cover_side` (external or internal), `solar_cover_shade` (light, medium, dark), an optional direct `solar_g_total` override, and the bare-glazing `solar_g_glazing` (default 0.70) — behind a `solar_properties_enabled` master toggle that is off by default. From those I derive an effective g for the glazing-plus-cover assembly at the cover's current position, blending shaded and unshaded transmittance by the fraction of glass the cover covers; the position-to-shaded-fraction map is a `CoverTypePolicy` hook rather than a cover-type branch, and it shares one `covered_fraction` primitive with the day/night shade engine. On top of that sits a diagnostic-category Estimated Solar Gain sensor reporting glass area × plane-of-array irradiance × effective g. A horizontal irradiance sensor is transposed onto the window plane through Erbs decomposition and isotropic transposition (`erbs_diffuse_fraction`, `plane_of_array_irradiance`, with DNI clamped to the extraterrestrial beam so a mis-scaled sensor can't produce an impossible beam term); a plane-mounted sensor passes straight through via the new `irradiance_plane` option. Glass area comes from its own policy hook and is `None` for cover types whose schema has no window width, so the sensor reports unknown rather than inventing one. The figure is an estimate, roughly ±30%, and every input term and its provenance rides in the attributes. Getting the raw watts this far meant extracting a shared float read out of the cloud-suppression threshold reader — which had been collapsing W/m² to two booleans and discarding the number — into a `ThresholdReading`, with a 43-case characterisation test written and run green against the old code first so the activate/release truth table and its fail-open path stayed put. Effective g derives from `PipelineResult.position`, never `final_state`, so an inverse-state install reports the same value as a normal one at the same physical position. A same-cycle follow-up (#1281, #1280) closed the unit hole: HA's `irradiance` device class also admits BTU/(h·ft²), so a genuine 600 W/m² arriving in imperial units computed to about 190 and the sensor silently reported a third of the truth. It now refuses rather than converting — `unknown` with `unsupported_irradiance_unit`, the observed unit echoed in attributes, and a once-per-situation coordinator warning naming the entity — and non-finite readings are treated as non-numeric, which also stops a `nan` or `-inf` from pinning the cloud-suppression latch on.

**Three-point tilt calibration for asymmetric venetian slat travel (#1222):** Specify Angles could only describe a linear map between the slat angle at 0% and at 100%, which misdescribes hardware whose slats pass horizontal somewhere other than the midpoint. `tilt_horizontal_percent` names the actuator percentage at which the slats are physically horizontal, turning the angle-to-percentage map into two affine segments hinged at that point; `0` is the disabled sentinel and reproduces the two-point behaviour byte-identically, so there is no migration. The same pass rewired the climate tilt path through the engine map the solar path already used — it had been applying MODE1's fixed 90° denominator and ignoring calibration entirely — and clamped `climate_tilt_percentage` to a strict 0–100 contract. Four audit rounds followed: an angle-space tie-break in `more_protective_position` that could swing a command by up to 82 points on symmetric pairs now measures through a shared `coverage_distance` metric, and an off-scale climate target (summer's fixed 45°, glare's 80°) resolves by direction to the nearest reachable end rather than by magnitude, so a drive that cannot reach the target keeps its own end instead of being sent fully closed.

**Named command queues serialize transmissions across covers (#1194, #1189):** Covers on one-way radio backends lose frames when independent config entries transmit at the same moment, and the only spacing that existed was the Cover Group stagger — group-scoped, and only on group-triggered fan-out — so routine per-entry solar tracking was entirely unthrottled. Covers now opt into a named queue on Movement & Schedule, and covers sharing a queue never transmit inside each other's spacing window. The gap belongs to the queue rather than the member: it is configured on a new Command Queue config entry, and a queue name with no matching entry still works at the `DEFAULT_COMMAND_QUEUE_GAP` of 5 seconds, so naming a queue never requires creating one. The gate's position is load-bearing — it sits between the physical-clearance gate and the booking call, because earlier deadlocks Model C dual-rail sequencing and later would burn the 5-second command grace against backend waits measured as long as 33 seconds — and a `COMMAND_QUEUE_MAX_WAIT_SECONDS` budget of 30 seconds means a withheld command transmits anyway rather than waiting forever. Safety-priority dispatch is head-of-line but still takes its spacing, since a storm retraction across many covers is the most collision-prone moment there is; unassigned covers hit one early-out and behave exactly as before. Three audit rounds hardened it: ownership now unwinds on any `BaseException` and a `QueueGrant` carries its own identity, so a cancelled dispatch can no longer strand the slot and leave every member burning the full budget and then transmitting simultaneously — the exact collision the feature exists to prevent. The spacing wait re-reads the busy deadline after each sleep so a venetian tilt tail keying its frame mid-wait is actually observed through `mark_external_transmit`, and the reconciliation pass carries one whole-pass allowance sized at half its interval, with `projected_wait_seconds` counting spacing owed plus a gap per reservation ahead, after a probe showed the naive version emitting at most one frame per pass and starving two of five off-target covers across twelve simulated minutes.

**Scope the venetian tilt-only carriage pin (#1330):** Tilt-only mode pinned the carriage closed for every automatic winner except the explicit-user set and DEFAULT, so a cloud-suppression or climate win forced position 0 — which for a tilt-only venetian on a door means the door is physically blocked on every overcast day. The new `venetian_tilt_only_scope` enum takes `all_automatic_control` (the default, today's behaviour) or `sun_tracking_only`, consumed as a fourth independent skip clause in `_pin_tilt_only_carriage` through a `_tilt_only_pin_applies` predicate that short-circuits on the default before reading the control method. Under `sun_tracking_only` climate winners are released alongside cloud suppression: the carriage rises, but the slats hold their last angle, since cloud suppression commands no tilt. I also corrected the `venetian_mode` description, which had promised the pin applied only while the sun was in the tracking window while the code pinned every automatic winner.

**Sensor-gated constraints that act outside the time window (#943, #1231):** A custom-position slot could only act outside the user's clock window by claiming the full safety bundle — auto-control bypass, delta-gate bypass, surviving `clear_non_safety_targets()` — which is far more authority than "keep this window's minimum opening overnight" needs. Each slot now takes a "Keep constraints active outside time window" opt-in, and only bounded claims ride it: min mode, position max, tilt min and tilt max. A FIXED claim — an exact position, Use My, tilt-only — never does, so the option can clamp a position but never drive one. The registry converts the computed winner into a pseudo-hold before axis judging, giving the constrained axis the bound edge and every other axis the cover's current read, with `may_act_outside_clock_window` as the single admission predicate and two new trace codes so the decision is visible. Four audit-driven fixes closed the coordinator's two pipeline-bypassing dispatch seams, a double-transform that sent calibrated installs to the wrong device value, and a tilt or Use My value leaking through on a position-only bound. A follow-up caught the option doing nothing at all in the most ordinary configuration of the lot (#1231): with a second custom slot winning at the same default priority of 77, `outranking` is strictly-greater, so the opted-in bound yielded to a "holder" that was holding nothing. `_as_outside_window_pseudo_hold` now passes a `PSEUDO_HOLD_HOLDER_PRIORITY` sentinel of -1, below every configurable slot priority and below `DefaultHandler`'s 0, so every real claim outranks it.

**Per-slot time-window scope for custom positions (#1318):** A FIXED custom-position slot had no clock gate at all, so after `end_time` it stayed the pipeline winner, tripped the active-override guard, and suppressed the end-of-window send — the cover simply stayed where the slot had put it. The per-slot `custom_position_scope_to_window` opt-in stands a slot claiming an exact position or Use My down once the clock window shuts; `DefaultHandler` then wins, the override guard returns False on its own, and the end-of-window position sends. Absent means today's behaviour, so the inverse request — a sleep-mode floor that has to survive the transition — keeps working. The safety slot at priority 100 is exempt inside the gate itself, and constraint-mode slots stay out of scope, since those are what the option above owns.

**A weather-override tilt for venetian blinds (#1297):** The weather override named only a position on its result, so the venetian policy's engine-tilt suppression left the slats wherever the last solar cycle put them — a shade retracted for a storm but still tilted wide open. The clearable `weather_override_tilt` lets the handler name a slat angle on its own result, through the same seam the custom-position handler uses, gated on a `weather_override_includes_tilt` policy ClassVar rather than a cover-type string. Day/night shade stays off it deliberately: its second axis is a fabric blend, not a slat angle. Min mode stays position-only, since there the handler defers and a lower-priority handler takes the seat, and an outranked handler must never drive the tilt axis. A follow-up found the runtime read wasn't gated the way the UI was, so a day/night shade holding a stray value from a prior venetian config was driven to that blend on every weather retraction; gating the read in the snapshot builder — the sole construction site — closes service calls, type switches and hand-edited entries at once.

**Scope the weather override to the time window (#1308):** Weather is one of only two producers of a safety result, and a safety result licenses a position to reach hardware after `end_time`. That is right for storm retraction and wrong for anyone running weather as a comfort rule, who had no way to stop it outranking the end-of-window and sunset positions. `weather_outside_window` defaults to True, so every existing entry is unchanged; opted out, weather stands down outside the clock window at both seats it can act from — the handler's exact-mode result and the min-mode floor, which had hard-coded its own outside-window flag. The gate keys on `clock_window_open` and never on `in_time_window`: the two disagree when the daytime gate reads dark mid-clock, and gating on the latter would strip storm protection at 10:00 on an overcast morning.

**Cloud suppression defers during the extreme-heat hold (#1272):** Cloud suppression runs at priority 60 and climate at 50, so on an overcast but hot afternoon suppression could win and open the cover to its default position while the sun was still in the window's field of view — exactly when the room is hottest and still taking direct sun. Fifteen minutes later the field-of-view guard stood suppression down, climate took the top match, and the extreme-heat hold closed the cover again; the reporter saw that open/close flip. Suppression now defers when climate would produce an extreme-heat result on the same cycle, resolved once per cycle in the snapshot builder as `climate_extreme_heat_active` and gated on climate mode being enabled, with `ClimateCoverData.is_extreme_heat` delegating to the same `resolve_extreme_heat_active` helper so the rule lives in one place. The trace reports `SKIP_CLOUD_DEFERRED_EXTREME_HEAT` so the deferral is visible in diagnostics. I deliberately did not reorder the handlers — suppression above climate is correct for summer cooling, winter heating and the low-light path — and the carve-out sits strictly after the field-of-view guard and strictly before the resolved-bool gate, so neither earlier fix becomes reachable differently.

**Blind spots publish their elevation gate (#1292):** The sun sensor emitted `blind_spot_range` and `blind_spot_ranges`, both pure azimuth, so the companion card could draw the wedge but had no way to say when the spot is actually active — the elevation gate was already sitting in the diagnostics configuration dict and was being dropped on the way out. `_sun_position_attrs` now also emits `blind_spot_slots`, one entry per active slot in the same order as the existing ranges, pairing each range with its `elevation` and `elevation_mode`, built in the same loop so the two attributes cannot drift apart. `elevation_mode` coalesces a `None` as well as a missing key, because the builder materializes that key unconditionally and the published gate has to match the gate the engine actually applies. The existing attributes are unchanged.

**The companion card install is offered in the options flow (#1261, #1168):** HACS declined the card's plugin submission on policy grounds, so it ships as a custom repository — users cannot find it by searching HACS, and the integration never mentioned the card at all. A Dashboard Card row on the cover options menu now reports whether the card is installed and at what version, and hands a missing install off to HACS through a My Home Assistant redirect, so HACS shows its own add-custom-repository confirm and then offers the download. I chose the redirect over calling into HACS directly: it registers no services, so the only Python route is an undocumented private call doing blocking GitHub I/O inside the flow. A new `companion_card.py` owns every fact about the card; detection reads HACS when it's running and falls back to the registered Lovelace resources, so a hand-installed card is never nagged as missing, and every read of both is guarded, because HACS is a custom integration with no versioned API and a shape change there must cost this one screen rather than the whole options flow. Three audit rounds went into the screens saying only what the router had actually established — `card_installed`, `card_installed_version` and `card_installed_update` are separate leaves each owning a full translation block, so a German or French user no longer gets an English sentence built by an f-string mid-paragraph.

**Custom slot names reach the config summary's rule lines (#1190):** The "How It Decides" rule line and its three inline footgun warnings hardcoded `Custom #{slot}` even when the slot carried a configured name — the priority chain had learned names in #910, and these five templates hadn't. I compute `_slot_label` once per slot, the configured name when present and a translated `custom.slot_label_default` fallback otherwise, and pass it to all five templates. The no-name path renders byte-identically in all three languages.

**Release tooling: a forward-merge check and a stale-checkout guard (#1250):** A new workflow fails when `main` carries commits that never reached `develop`, on every push to develop and on a daily cron, which is the divergence a skipped post-release forward-merge creates. `validate_branch_freshness` in `scripts/release` refuses to cut a release from a checkout that is behind or diverged from its origin counterpart, since the script tags and pushes whatever tree is checked out; it runs before and independently of the branch-name check, and `--force-branch` waives only the name check, never staleness. Tooling only — no file under `custom_components/` is touched and nothing about a running install changes.

## Fixed

**`is_safety` now has a defined lifetime instead of surviving until the next dispatch (#1165, #1225, #1311, #1313):** `PerEntityState.is_safety` had three writers with three different rules and no writer that cleared it when the safety condition ended, so a stale True survived `clear_non_safety_targets()` and let `run_reconciliation_pass` resend with automatic control off or outside the time window. The same-position skip books a target with no dispatch behind it and wrote nothing to the flag, so a skip-booked target inherited whatever the last real dispatch left; `_execute_command` called `_prepare_service_call` without `is_safety` or `use_my_position`, so the first resend of a safety target cleared its own flag and every later pass skipped it, while a My-route cover fell past the My branch to the open/close threshold and resent a My position of 10 as `close_cover`, rebooked as 0. The verdict is now written on every entry into the skip branch, `is_safety` is threaded through from the reconciliation record, and `use_my_position` is re-derived through a pure `is_my_preset_target()` rather than stored on a sixth booking site. Three audit rounds settled the asymmetry between the two polarities: revoking only removes a licence, so it happens unconditionally, while granting hands one out and so attaches only to the number the safety decision actually produced. Three sibling gaps close alongside. An external `stop_cover` books a My target, which is a user action and not a safety decision, so it revokes unconditionally at the booking through a new public `revoke_safety_verdict` (#1225) — previously that My number inherited the prior verdict and, if the user pressed stop while a safety dispatch was mid-move, came out marked safety-protected on the strength of a decision about a different number. The coordinator's closed-clock early return never reached the code that writes a verdict, so with the weather override scoped out of the window a daytime weather booking crossed the closing edge still licensed and reconciliation resent it overnight; it now revokes at that call site, before the outside-window sweeper, since a row carrying both flags is spared by the sweeper while it still reads as safety (#1311, which also renamed `clear_safety_targets` to `revoke_safety_verdicts` now that it shares the single write funnel). The force-send path asked the same admission question and returned without revoking, so both closed-clock exits now funnel through one `_revoke_stale_closed_clock_licences` helper (#1313).

**Publish-lag guards for venetian tilt-only and day/night blend sends (#1329, #1333):** A venetian tilt-only send never stamps a position command, by design, so it opened no manual-override suppression window at all — once the five-second command grace expired, the actuator's own late re-publish of the tilt it had just settled at read as a manual move, and the reporter's cover sat falsely overridden for nearly two hours on a 4% delta. The tilt axis now gets its own window anchored to `_tilt_sent_at`, capped at `VENETIAN_TILT_VERIFY_TOLERANCE` — the same band the verify path already treats as arrived — and wired through a non-consuming `single_axis_suppression` callback rather than the cross-axis suppression seam, since a tilt-only send never moves the carriage. The stamp moved to after the successful service call, so a failed send leaves no stale anchor. Day/night shade drives the same sequencer but carried the pre-fix body and never wired the check in, so a blend-only send had the identical hole; the OR-composition is now one `resolve_single_axis_suppression` both policies delegate to, and day/night also forwards `backrotate_publish_lag_seconds` into its sequencer attach, which venetian did and it didn't — the window had been pinned at the 45-second default no matter what the user configured (#1333).

**Rail-interlock corrections are keyed by pair, and the leader keeps its own target (#1154, #1156):** The interlock that corrects a Day/Night Model C follower after a command aimed at its partner registered nothing, so ACP's own user seams got an awaited inline execution with none of the supersede-and-cancel guarantee the external listener has — two card-slider drags on the same rail produced two live corrective sequences racing each other with overlapping engage/complete brackets. The cancel-prior-and-register block moved into a shared `_start_interlock_task` used by both writers, and `_external_interlock_tasks` is re-keyed from the follower entity to a `frozenset` of the unordered pair the correction actually moves, with the user seam awaiting the registered task and translating a supersede-cancel into a skip rather than a silent drop. Separately, `plan_external_command_interlock` built every plan with the follower's target as the leading target, which is wrong whenever the leader holds a kept, still-honest target of its own — a dispatch that raised leaves exactly that state, and because the booked-target accessor is gated on waiting-for-target, the kept value was invisible to the clearance check and the correction overwrote the user's 40 with the follower's 70. A new unconditional `get_command_target` accessor now feeds the same clearance inequality, so a recorded target that clears the follower is used, one that doesn't falls through, and no recorded target behaves as before (#1154).

**Hold verdicts are judged in the right frame and against the right position (#1230, #1175, #1179):** `_judge_position_axis` compared a raw device-frame read against logical, user-configured bounds. Un-inverting only undoes inverse state, and inversion is suppressed outright on a calibrated install, so nothing unwound the interpolation curve: on a 20–80 curve, device 42 is logically 36.67 and violates a logical floor of 40, but the judge saw 42 ≥ 40 and called it compliant, silently not enforcing the floor (and mis-firing a ceiling the other way). I added `from_cover_frame` to the position utilities as the algebraic inverse of the dispatch chain, plus an `InterpolationCurve` on the snapshot as `interp_curve`, so the pure pipeline can un-map a read with no coordinator handle; it defaults to `None` and reduces to exactly the old behaviour for uncalibrated installs, and a non-monotonic curve skips un-interpolation rather than raising (#1230). The Target Position sensor had the mirror-image problem: it preferred `held_position` unconditionally, which is right while a hold is holding and wrong the moment a bound outranks the holder and clamps it — the registry writes the clamped value into `position`, sets `position_constraint_applied` and clears the skip in one replace, so ACP sent 80% while the sensor still said 50%. The preference is now gated on `position_constraint_applied`, and the three surfaces that each derived "the target" separately — the sensor value, the distance attributes, and `all_at_target`, which had been measuring against the raw state and so read a group parked exactly where a hold holds it as not at target — all resolve through one `_target_position` helper (#1175). And the coupled half of the per-cover hold judgment, deliberately deferred out of 2026.8.0 and listed there as a Known Limitation, is closed: a new polymorphic `hold_reference_position` hook reduces a coupled instance to the one number that answers for it, so `_judge_position_axis` becomes three-way — independent policies keep the per-cover path, a policy that names a reference has that number judged, and a coupled policy with no single answer keeps the entry mean as a fallback. Day/night Model C reports the bottom rail, Model B decodes the split-range wire to coverage (which also fixes a clamped hold being dispatched unfolded), and Model A and a front-less dual panel turn out to be independent and gain the per-cover fix outright. An audit round then caught a real stale-state race in Model B's fabric stash and gated the fallback on the winner actually carrying a held position (#1179).

**The vertical safety margin was inflating the contract it was meant to protect (#1173):** On the vertical axis, position is the exposed glass band and the projection already lands exactly on the shaded-distance boundary with zero headroom, so multiplying it by `SafetyMarginCalculator`'s ≥ 1.0 multiplier opened the blind further and let more sun in — the opposite of the docstring's stated intent. It was never a safety margin on that axis, only an inflation of the violation, and it survived because nothing asserted the contract until #1169 added one in the previous cycle. I removed the multiply from the vertical `calculate_position()`, deleted the unused delegate, and pinned the margin at 1.0 on all three trace paths so the diagnostic key keeps its contract; the multiplier itself is untouched, since the tilt axis applies it correctly, in the closing direction and under user control. This drops the 16 strict-xfail cases in `tests/test_geometric_accuracy.py`, so that contract test now runs 216 of 216, and adds two guards the suite never had — one asserting the vertical margin can never increase penetration, one pinning the no-op inside the everyday envelope. Covers close slightly further at gamma past 45° or outside 10–75° elevation; inside that envelope output is unchanged. This is the item 2026.8.0 documented as an open Known Limitation. A user-configurable vertical margin mirroring the tilt axis is tracked separately in #1220.

**A tilt-only custom-position slot with no fixed tilt keeps its bounds (#1215):** v2026.8.1 already fixed the previous cycle's regression where dropping `tilt` from the registry's mergeable set left sunset tilt and default tilt unreachable whenever a DEFAULT-labelled handler won, via `compute_default_tilt()` (#1214). This range closes a sibling gap in the same family: a custom-position slot with tilt-only enabled, no fixed slat angle and a configured tilt minimum went completely inert — it claimed no position, emitted no constraint and never clamped the solar tilt, because the tilt-only flag conflates always disclaiming the position axis with outranking the tilt bounds, and with no angle named that FIXED claim is vacuous. One shared `has_fixed_tilt()` predicate now keys the precedence on an actual fixed tilt at all three sites, the position-axis disclaimer stays on the bare flag, and the summary stops rendering a phantom "slat fixed at 0%" — plus new warnings for the two silent footguns in the same family. Existing configs are fixed with no user action and no migration.

**#1196 already shipped in v2026.8.1:** The fix that stopped `ClimateHandler.evaluate()` stamping a season label (SUMMER/WINTER) onto a non-season strategy reaching the label chain — a low-light fall-through reporting SUMMER, tilt glare control reporting SUMMER or WINTER with the sun still in the field of view — landed in the v2026.8.1 patch behind a `_SEASON_STRATEGIES` frozenset gate. No new behavior ships for it in this range.

**Cloud-suppression hold time now reaches climate's low-light branch, and the first reading after a reload is committed (#1238, #1264):** The `cloud_suppression_hold_time` debounce gated only the suppression handler's own resolved bool, so the climate handler's low-light branch one priority below evaluated the same lux and irradiance readings raw and moved the cover in the very cycle the "holding 600 seconds" line was logged. I reused the smoothing seam the temperature crossings already had: `ClimateCoverData` gains `low_light_active` with an `is_low_light` property, threaded from the snapshot's resolved suppression bool only when suppression is enabled, so installs with it off are byte-identical. Three deliberate changes ride along — the hold is now symmetric and applies to the release edge, cloud coverage joins the low-light trigger set, and a configured lux release band latches low light. That work also gave `HoldDebouncer.reset()` a `seeded` keyword so the cloud manager commits its first observation in line; `ClimateSmoothingManager` then turned out to need the same thing and hadn't got it (#1264), so a restart during genuinely cold weather left the resolved winter flag False and sun-tracked for the whole configured hold before the smoothed flag caught up. It now passes `seeded=False` from both its constructor and its reset, and the reset also runs on a transient readings outage, where seeding would have re-armed a fresh full hold after a one-cycle blip.

**A second pass on the cloud-suppression summary and the position explanation (#1314):** v2026.8.3 already fixed the summary rendering "skips sun tracking when weather in {sunny, partlycloudy, clear}" backwards — `cloud.weather_in` now reads "weather not in {…}" in all three languages (#1301). This range adds three more follow-ups to the same surfaces. The position explanation took its outside-the-window early return from the flag that ANDs the clock with the daytime gate, while every real dispatch guard reads the clock alone — so on a gate-dark but clock-open cycle the sensor announced "commands paused" while the computed position was being dispatched, and `_determine_control_status` carried the identical bug, so the two fields contradicted each other on the same cycle. Both now key on a `clock_window_open` field threaded onto `DiagnosticContext`. The outside-window note also replaced the winner's own reason rather than qualifying it, so a manual override rendered as "Outside time window → default position 50%", discarding that a manual hold had won and inventing a position nobody held; it is now a trailing clause, except for a genuine DEFAULT winner, which still collapses to the note alone. And the summary's weather-state fragment was joined into the same comma list as the lux, irradiance and coverage triggers, reading as a fourth independent OR when it is really the lowest rung `_read_sunny` falls through to; it now nests as a `cloud.weather_fallback` suffix on the `is_sunny` fragment, staying a peer only when the weather list is the sole source.

**The sunset edge is now keyed on the configured boundary, not the clock window's close (#1287):** The sunset-active flag means "a night-type default is in effect" and covers both the end-of-window position and the sunset position, but the transition tracker used it as its sunset-edge detector — so the latch flipped at clock `end_time` instead of at the configured sunset boundary. An entry with a 19:00 end, a 60% end-of-window position and a 16% sunset position due at 22:04 dispatched both 0.3 seconds apart at 19:00, and the genuine 22:04 edge was swallowed by the already-consumed latch. A new `resolve_sunset_verdict` returns the two facts separately as a `SunsetVerdict`, `compute_effective_default` delegates to it unchanged, and the tracker now reads the boundary fact directly. (v2026.8.2 already shipped the two neighboring time-window fixes in this same area: #1256, a blank start time anchoring to sunrise instead of midnight, and #1241, refreshing the pipeline before the end-time override guard.)

**The occupancy countdown's remaining gap, and the `motion_status` sensor's own "holding" state (#1266, #1162):** v2026.8.3 already fixed the occupancy sensor deriving its timeout end time from the occupancy _detection_ stamp instead of the no-motion timer's own _clear_-edge start — `MotionManager` now stamps `_timeout_started_at` when the timer starts and owns the formula behind a `timeout_end_time` property the sensor publishes verbatim. This range closes the half that fix left open: `_on_motion_timeout_expired` set the active flag without clearing that same stamp, so the property kept returning a past timestamp for the entire no-occupancy state once the countdown legitimately ended, and the card kept rendering "expires in expired" indefinitely instead of only during the live countdown. All four exits from "timer counting" now clear the stamp; the attribute name and payload shape are unchanged. In the same subsystem, the `motion_status` enum sensor declared five options while `_motion_status_value` could return a sixth — HA raises on an undeclared enum value rather than publishing it — and the branch that would have returned it compared the control method against a string no member carries, so it was dead code and the sensor reported no-motion where it should have reported holding (#1162). Both halves are fixed, and a static AST guard now scans every enum sensor's value function for string literals absent from its declared options.

**Commands that the cover hasn't reacted to, and reversals that look like settles (#1139, #1306):** A cover that has not yet reacted to a dispatched command republishes its pre-command position with an unchanged state string, which fell straight through to the unconditional clearing of the wait-for-target flag — opening the manual-override gate on that same drained event and reading the entire commanded travel as a manual move. Reproduced both on a serialized RTS command queue and on a single cover whose own actuation lag outruns the five-second grace. `position_at_send` is now stamped at both dispatch writers, and a new arm holds wait-for-target while the reported position still equals the position at dispatch, requiring the previous position to match too so a symmetric straddle still reads as genuine movement; the arm records no progress and starts no new grace, staying bounded by the existing transit-timeout backstop (#1139). The mirror case is a cover that acks and then reverses: two independent suppression arms judged causation from position numbers alone, and a Velux/KLF-200 reversal — which publishes no intermediate positions — satisfied both, so the flag stayed set, the override manager rejected the event, and the pipeline re-sent the command for six consecutive cycles in the reported trace. Both arms now consult one `_is_reversal_after_ack` predicate: the cover entered transit and left it without getting closer to the target, with the equal-distance case discriminated by whether it has moved away from where it started (#1306).

**Manual-override detection accuracy (#1275, #1273):** A full read of the subsystem turned up six defects rather than a user report. The two override axes disagreed exactly at the threshold — the primary rejected on `<=` and the secondary marked manual on `>=` — where strict `>` is correct on both, since the threshold floors at `POSITION_TOLERANCE_PERCENT`, the same constant the arrival test uses, and a delta that counts as arrived must not also count as a touch. Three `PositionDeltaDetector` reason strings described a comparison their own branch didn't perform. The 24-hour suppression counter pruned its window only on write, so the published count froze at the last suppression instead of decaying, misdirecting users toward raising the publish-lag setting for an actuator that had long since settled; a shared `_prune_suppressions` now serves the reader as well. The expiry accessor promised `None` for a cover not held while gating on the timestamp alone, so arming now writes the flag and the timestamp through one seam. And the restore path parsed an untrusted timestamp bare, so a malformed or naive value raised out of entity setup and cost every other cover its restored override; `_parse_restored_expiry` validates and skips with a warning instead.

**#1232 already shipped in v2026.8.2:** The fix for a restored manual override being destroyed on every reboot — the coordinator truthiness-testing a tri-state restore flag so `None` (no switch restored yet) read as the user having explicitly disabled detection — landed in the v2026.8.2 patch. No new behavior ships for it in this range.

**Inverse-tilt covers stopped seeing phantom manual overrides (#1227):** Thanks to [@slangeder](https://github.com/slangeder), who reported and diagnosed this from a KNX fleet running venetians through a 1Home HomeKit bridge, with event-timeline captures showing the reported tilt as exactly 100 minus the expected one on every false override. `SecondaryAxisCheck.evaluate` compared the logical dispatched tilt against the raw published `current_tilt_position`, which is the wire value — with inverse tilt the two differ by 100 − x, so a fully verified tilt read as a delta of `|2x - 100|` and fired a false override: dispatched logical 96, actuator publishes wire 4, delta 92. Every sibling reader already paid the inverse; the delta comparison was the one place that didn't. The reported value is now normalised through `flip_if` before the comparison, wired from both the venetian and day/night policies through a public `DualAxisSequencer.tilt_inverted` property — day/night had no normalisation at all and produced 92 where venetian produced 0, reachable because config import merges public keys with no cover-type filter. The excursion path deliberately keeps matching on the raw wire value, since the drift-reset trajectory tracker compares wire-space records on both sides.

**#1234 already shipped in v2026.8.2:** The fix for the drift-retry re-send not threading `drift_reset_eligible` — which re-armed drift accumulation on a send the sun-tracking-only scope had already ruled ineligible — landed in the v2026.8.2 patch. No new behavior ships for it in this range.

**The vertical sill offset is now perpendicular (#1290):** The elevation offset returned a ray path length, which the position calculation subtracted from a perpendicular depth and the projection helper then divided by the cosine of gamma a second time — over-subtracting the sill by that same factor at every gamma other than zero. The effective distance went negative, the clamp pinned the position at 0, and the blind sat at its sun-tracking minimum all afternoon. `_elevation_offset` now takes gamma and multiplies by `clamped_cos_gamma`, returning an offset in the same units as the distance it is subtracted from; one helper change fixes both call sites, and a `sill_height` of 0 stays an exact no-op. Two earlier issues had patched this symptom at the wrong end without spotting the units mismatch.

**#1291 already shipped in v2026.8.3:** The fix that widened the diagnostics-builder sub-key tuple so signed-gamma blind-spot keys actually reach it — every configured blind spot had been publishing no range at all, with the engine still computing the right position from raw options — landed in the v2026.8.3 hotfix. It's the fix the per-slot elevation gating above builds on; no new behavior ships for it in this range.

**#1267 already shipped in v2026.8.3:** The fix that let a cleared Motion Template field, a cleared interpolation range, and a cleared blind-spot gamma or elevation field actually stay cleared — via `optional_entities()`, inserted after each options-flow step's validation early-return — landed in the v2026.8.3 hotfix; no new behavior ships for it in this range.

**`cloudy` dropped from the weather-state default (#1300):** The shipped default for Weather Conditions was `["sunny", "partlycloudy", "cloudy", "clear"]`, contradicting the field's own help text in two places, and with `cloudy` pre-selected that state alone never contributed to the cloud-suppression trigger — the option was inert for the condition it names. I pulled the three duplicated literals into one `DEFAULT_WEATHER_STATE` constant, reworded the help text in all three languages, and added a parity guard that parses the enumerated defaults out of the English text and compares them against the constant. This is a schema default only: an existing config entry already persists its own list, so nothing moves for current installs and there is no migration — it changes what a new install starts with.

**Logs name the handler that actually won (#1263):** The dispatch reason for any non-bypass pipeline winner was the literal string `solar`, so a move decided by climate or the glare zone still printed as a solar positioning line and emitted `trigger: "solar"` on the command events. The reason now reuses `pipeline_winner_name`, which reads the decision trace's matched step and already backs the group who-won sensor; the control method was rejected as a substitute because the low-light branch deliberately reports DEFAULT, which would have mislabelled the motivating case all over again.

**Service field/translation parity is now locked across all 37 services, not just two (#1251):** v2026.8.2 already fixed one instance of this drift in `set_position_limits` — `min_position_sun_tracking` missing from `services.yaml`, and `enable_position_matching` missing its translation entry (#1242). Only `set_blind_spot` and `set_position_limits` had a hand-written parity guard, so the other 35 services could drift the same way silently, which is how #1242 shipped twice. One parametrized test now covers the union of `services.yaml` and every language's `en.json` for all 37 services, and three more drifts are fixed with it: `set_light_cloud` gains its is-sunny sensor field, `set_venetian` gains the back-rotate publish-lag field with bounds asserted against `OPTION_RANGES`, and `set_geometry` loses a stray translation entry for a field it doesn't expose. ## Compatibility

Home Assistant 2026.3.0+ and Python 3.11+. `ConfigFlowHandler.VERSION` stays 3 and `MINOR_VERSION` reaches 21; every migration block this cycle is an additive no-op bump, so nothing is rewritten in an existing config entry and a rollback finds its configuration exactly as it left it. New options — the tilt-only carriage scope, the per-slot window scope, the weather override's tilt and window scope, the solar properties, the command queue, three-point tilt calibration — all read as their pre-existing behaviour when absent, so upgrading changes nothing on its own. The one changed default, dropping `cloudy` from the weather-state list (#1300), is schema-only and applies to new installs; existing entries keep the list they already persist. The companion Lovelace card ([jrhubott/adaptive-cover-pro-card](https://github.com/jrhubott/adaptive-cover-pro-card)) is a separate repo with its own release cycle and needs no update for this release.
